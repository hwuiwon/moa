# S02 — Add `cargo-hakari` workspace-hack

## Scope

Introduce a `workspace-hack` crate generated by `cargo-hakari` to deduplicate transitive dependency feature unification across the workspace. Expected outcome: 20–25% faster incremental builds during the rest of the refactor.

## Preconditions

- S01 is complete and merged.
- `cargo check --workspace` is green.

## Why this prompt

When multiple workspace crates depend on the same transitive crate (e.g. `tokio`, `serde`) but with different feature sets, Cargo unifies features per build target — which means a `cargo build -p moa-cli` and `cargo build -p moa-brain` may compile `tokio` *twice* with different feature unions, wasting build cache and CPU. `cargo-hakari` solves this by creating a small "hack" crate that depends on the union of all features, forcing Cargo to use a single unified build of every transitive crate.

This is well-known practice in large Rust workspaces (used by Diem, Mozilla's Servo, Cargo itself). The setup cost is one prompt; the maintenance cost is zero in steady state (CI re-generates).

## Files in scope

- New crate at `crates/workspace-hack/` (one Cargo.toml, one src/lib.rs)
- Root `Cargo.toml` (add to `[workspace] members`)
- Every workspace crate's `Cargo.toml` (add `workspace-hack` as a dependency)
- New CI step (or note in `REFACTOR_NOTES.md` if CI config is out of scope)

## Files explicitly out of scope

- Any source `.rs` file outside the new `workspace-hack/src/lib.rs` (which is empty)
- Test changes
- Any production code

## Step-by-step instructions

1. **Install cargo-hakari** if not already installed:
   ```bash
   cargo install cargo-hakari --locked
   ```

2. **Initialize at the workspace root**:
   ```bash
   cargo hakari init --yes
   ```
   This creates `crates/workspace-hack/` and a `[workspace.metadata.hakari]` section in the root `Cargo.toml`.

3. **Configure hakari**. In the root `Cargo.toml`, ensure `[workspace.metadata.hakari]` contains:
   ```toml
   [workspace.metadata.hakari]
   hakari-package = "workspace-hack"
   resolver = "2"
   platforms = ["x86_64-unknown-linux-gnu", "aarch64-apple-darwin", "x86_64-apple-darwin"]
   # Add any other platforms you build on
   ```

4. **Generate the hack crate contents**:
   ```bash
   cargo hakari generate
   ```

5. **Wire `workspace-hack` into every workspace crate**:
   ```bash
   cargo hakari manage-deps --yes
   ```
   This adds `workspace-hack = { path = "../workspace-hack", version = "0.1" }` to every workspace crate's `[dependencies]`.

6. **Verify hakari is fully applied**:
   ```bash
   cargo hakari verify
   ```
   Must report "the workspace-hack contents are up-to-date".

7. **Add a CI hint or note**. If the repo has a CI config (`.github/workflows/`, etc.), add a step to run `cargo hakari verify` so PRs that change deps remember to regenerate. If CI is out of scope, document this requirement in `REFACTOR_NOTES.md` under `[S02]` so it's not forgotten.

8. **Run full verification** (block below).

## Verification

```bash
cargo hakari verify
cargo check --workspace --all-targets
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace --no-run
```

Then a soft benchmark:

```bash
# Clean build, then incremental
cargo clean
time cargo check --workspace
# Touch one file, rebuild
touch crates/moa-core/src/lib.rs
time cargo check --workspace
```

The incremental rebuild should be noticeably faster than before S02. If it's *slower*, hakari is misconfigured — back out.

## Acceptance criteria

- [ ] `crates/workspace-hack/` exists with hakari-generated contents.
- [ ] Every workspace crate has `workspace-hack` in `[dependencies]`.
- [ ] `cargo hakari verify` passes.
- [ ] `cargo check --workspace --all-targets` passes.
- [ ] Incremental build time is at least not regressed (ideally improved).
- [ ] CI is updated or `REFACTOR_NOTES.md` has the maintenance note.

## Rollback plan

```bash
cargo hakari disable  # tells hakari to leave deps alone
# remove [workspace.metadata.hakari] from root Cargo.toml
# remove crates/workspace-hack/ from members and from disk
# remove `workspace-hack = ...` lines from every crate's Cargo.toml
```

## Notes for the agent

- **The `workspace-hack` crate is intentionally empty.** Its `src/lib.rs` is just `// generated by cargo hakari`. Don't add code to it.
- **`workspace-hack/Cargo.toml` is auto-generated.** Never hand-edit it. If features diverge, run `cargo hakari generate` again.
- **The hack crate's version stays at `0.1.0`.** It's never published.
- **If `cargo hakari verify` ever fails on CI**, the fix is `cargo hakari generate && cargo hakari manage-deps`, then commit.
- **Compile-time wins are larger after S08+** when more crates have been split. Don't expect a huge win after just S01–S02 alone.
- **Do NOT skip the `manage-deps` step** in step 5. Without it, the hack crate exists but does nothing.
- **If a platform is missing from the `platforms` list**, hakari may fail to unify deps that are platform-conditional. The list above covers Linux x86, macOS Apple Silicon, macOS Intel — extend if your CI builds on Windows or other targets.
