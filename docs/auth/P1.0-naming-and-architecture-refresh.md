## Steps

### 1. Author ADR-0002

Create `docs/architecture/decisions/0002-auth-architecture.md` following the
exact heading structure of ADR-0001. Status `Accepted`, date is today's date,
no supersedes line (this is a net-new decision).

Required content:

**Context** — Three paragraphs:

1. MOA needs identity (who is calling), authorization (what they can do), and
   security audit (what they did). The Phase 1 surface is API keys, SSO,
   SCIM, agent identity, fine-grained authorization, async approvals, and
   OCSF security-event logs.
2. The deployment matrix is two-by-two: multi-tenant SaaS (primary) and
   self-hosted single-tenant (secondary), each of which can optionally
   integrate Auth0 for SSO/SCIM/Token Vault. Self-hosted single-tenant must
   work with zero external dependencies.
3. The decision matrix has two independent axes: authorization engine
   (OpenFGA vs Auth0 FGA vs other) and identity provider (local API keys vs
   Auth0 vs generic OIDC). These are resolved independently below.

**Decision** — Numbered list (mirror the seven items in P00's "Key decisions
locked in" section). Be explicit:

1. **Authorization engine: OpenFGA self-hosted (Postgres-backed).** One FGA
   store per deployment, tenants are a relation. Auth0 FGA is a deferred
   swap-in option (Phase 4) with an identical API surface.
2. **Identity provider abstraction**: `AuthProvider`, `TokenVaultProvider`,
   `AsyncAuthzProvider` traits in `moa-core::traits`. Defaults are
   `LocalAuthProvider` (API keys), `NullTokenVaultProvider` (returns
   `NotConfigured`), `BuiltinAsyncAuthzProvider` (in-app approvals via
   Restate awakeable). Auth0 implementations live in a separate optional
   crate behind a Cargo feature.
3. **AI agents are first-class principals** with their own FGA subject
   identity (`agent:<uuid>`).
4. **`X-Moa-*` identity headers** propagate identity from `moa-edge` to
   `moa-orchestrator`. The orchestrator trusts these headers. The
   orchestrator's Restate handler port (`9080`) must not be exposed to the
   internet in production.
5. **Transactional outbox** for Postgres↔FGA consistency. No direct FGA
   writes from handlers.
6. **`make dev` brings up OpenFGA by default.** Contributors who explicitly
   want a leaner stack can set `MOA_SKIP_FGA=1`. Self-hosted single-tenant
   deployments ship embedded OpenFGA + its own Postgres database (logical
   DB on the same Postgres cluster).
7. **Naming**: HTTP edge crate is `moa-edge`. OCSF security-event crate is
   `moa-ocsf`. These names avoid collision with the existing `moa-gateway`
   (messaging adapters) and `moa-lineage-audit` (data-lineage Merkle) crates.

**Consequences** — Both lists, following ADR-0001's pattern:

*Positive:*
- Self-hosted deployments work without an Auth0 account or any external SaaS
  identity dependency.
- OpenFGA's API matches Auth0 FGA's, so migration to a managed engine is a
  config change, not a rewrite.
- Provider abstraction means Auth0 work is additive; no part of MOA is
  hard-coupled to a vendor.
- Agents as first-class principals avoid the "service account under a user"
  anti-pattern that complicates delegation auditing.
- Putting trait interfaces in `moa-core::traits` (consistent with the
  existing `CredentialVault` trait per `docs/architecture/type-placement.md`)
  keeps downstream crates from pulling in provider implementation
  dependencies they do not use.

*Negative:*
- Operating OpenFGA in self-hosted deployments adds an additional service
  to the local stack. Mitigated by `MOA_SKIP_FGA=1` for non-auth work and
  by the embedded-with-postgres bundling for production self-hosted.
- The orchestrator's header-trust model relies on network isolation of port
  9080. A misconfigured deployment that exposes 9080 to the internet would
  bypass authz entirely. Documented in a runbook; enforced by deployment
  templates in Phase 1.
- Two audit pipelines now coexist (`moa-lineage-audit` for data lineage,
  `moa-ocsf` for security events). Naming discipline matters; both ship to
  S3 via the same `audit-shipper` service (extended in P1.10).
- API keys, not OAuth tokens, are the default authentication. Keys cannot
  bind to a fine-grained user attribute set the way an OIDC ID token can.
  Mitigated by storing scopes as FGA tuples (key narrows user permissions)
  and by encouraging Auth0 mode for multi-tenant production.

**Mitigations** — Mostly redundant with Consequences; keep this section
short. Cover:

- ADR-0002 supersedes any conflicting prose in `docs/01-architecture-overview.md`
  and `docs/08-security.md`. Both are updated in this prompt to match.
- The deployment runbook (P1.10 prompt territory) will require that any
  production deployment template explicitly binds the orchestrator handler
  port (`9080`) to an internal-only interface or service-mesh network.

**Revisit conditions** — Bullet list:

1. A customer requests a deployment posture where SSO is mandatory and API
   keys are forbidden. Auth0/OIDC providers already cover this; ADR does
   not need revisiting unless the customer needs a third identity provider.
2. OpenFGA performance becomes a bottleneck at scale (Notion-class load).
   Either shard OpenFGA per region, or migrate to Auth0 FGA managed.
3. A regulator requires that identity propagation between services is
   cryptographically signed, not merely header-trust over an isolated
   network. Add JWT signing between edge and orchestrator.
4. A third audit pipeline shape is requested (e.g., SIEM-native CEF/LEEF
   instead of OCSF). Re-examine the `moa-ocsf` naming and shipper
   architecture.

**Re-introduction sketch** — Not applicable; this is an additive decision.
Omit the section or replace with a short "if this ADR is reversed" sketch
naming the dependent prompts (P1.1–P1.10).

### 3. Refresh `docs/01-architecture-overview.md`

Walk the doc top-to-bottom and:

a. Remove any references to the retired local-orchestrator crate. The crate was deleted
   in PR #186 (2026-05-08). Replace any "local orchestrator runs in-process"
   prose with a note that local development uses cloud Restate via
   `make dev`.

b. Find the crate inventory section (or add one if missing) and add the
   auth-pack crates. They live under the `crates/moa-auth/` namespace folder
   where noted, but keep package names unchanged:

   - `moa-auth/authz-schema` (`moa-authz-schema`) — typed FGA tuple keys and schema v1 constants (P1.1)
   - `moa-auth/fga-bootstrap` (`moa-fga-bootstrap`) — idempotent OpenFGA store + model bootstrap binary (P1.1)
   - `moa-auth/authz` (`moa-authz`) — FGA client, transactional outbox, outbox poller (P1.2)
   - `moa-edge` — public-facing HTTP edge: token validation, identity header
     injection (P1.3)
   - `moa-auth/providers` (`moa-auth-providers`) — local API keys, disabled auth, builtin approvals, null token vault, and provider bundle construction (P1.5/P1.6)
   - `moa-auth/auth0` (`moa-auth-providers-auth0`) — optional Auth0 implementations of the
     provider traits, gated by the `auth0` Cargo feature (P1.7)
   - `moa-ocsf` — OCSF v1.3 security-event types, emission helpers, signing (P1.10)

c. Add a new section titled "Auth Layer" near the security or data-model
   sections. Three subsections, one paragraph each:

   - *Identity* — `moa-edge` validates API keys (default) or OIDC tokens
     (Auth0/OIDC modes), injects `X-Moa-Identity-Type` /
     `X-Moa-Identity-Id` / `X-Moa-Tenant-Id` /
     `X-Moa-Acting-On-Behalf-Of` / `X-Moa-Api-Key-Id` headers, and forwards
     to the orchestrator. The orchestrator trusts these headers. Port 9080
     must be network-isolated.
   - *Authorization* — OpenFGA (Postgres-backed) is the default. The
     authorization schema (v1) lives in `moa-authz-schema` as Rust
     constants. Handlers call `require_authz(authz, identity, object_type,
     object_id, relation)`. No procedural macros; explicit calls only.
   - *Audit* — OCSF v1.3 security events written synchronously to a
     Postgres `security_events` table, shipped to S3 by the existing
     `services/audit-shipper` (extended in P1.10) with per-tenant bucket
     routing and Object Lock compliance mode.

d. Reference ADR-0002 inline ("see ADR-0002").

## Notes

- **Why this is its own prompt.** Every later auth prompt references the
  decisions made here. Trying to bake them into P1.1 implicitly means each
  later prompt has a "well, the ADR says..." dependency on something that
  was never written down. The 30 minutes spent on this prompt saves hours
  of "what did we decide again?" later.
- **ADR style is non-negotiable.** ADR-0001 sets the pattern. Mimic it.
  Reviewers expect Status/Date/Context/Decision/Consequences/Mitigations/
  Revisit. Do not invent a new format.
- **"OpenFGA by default" means operationally, too.** `make dev` brings up
  OpenFGA. The ADR makes this explicit so P1.1 cannot accidentally hide it
  behind a `dev-auth` target.
- **Self-hosted single-tenant ships OpenFGA.** Decided in Step 1.f. The
  alternative was a null/local authz provider that allows-all in single-
  tenant mode; rejected because it creates two different security postures
  that diverge over time. Better to standardize on OpenFGA everywhere and
  use embedded Postgres tables for the FGA backend.
- **The `audit_security` config section name** is chosen to disambiguate
  from the existing `[observability.lineage]` section (which configures the
  Merkle lineage audit). Resist the temptation to call this section
  `[audit]` — it is specifically for OCSF security events.
- **Resist scope creep.** This prompt produces no Rust code. If you find
  yourself drafting trait signatures, you are in the wrong prompt; that
  work is P1.2.
