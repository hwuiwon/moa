# P1.8 — Token Vault, Agent-as-Principal, and Auth0 CIBA

## Purpose

Three independent capabilities that share a single Cargo feature and a
single set of integration tests:

1. **Token Vault** — `Auth0TokenVaultProvider` retrieves third-party
   access tokens (Google, GitHub, Slack, ...) on behalf of users. Agents
   use this to call APIs the user has consented to, without MOA ever
   storing the tokens itself.

2. **Agent-as-principal lifecycle** — agents are first-class FGA subjects
   per the schema; P1.4 added the minimal table; P1.8 adds templates,
   registration, delegation grants (`can_act_as`), deactivation, and the
   full handler surface.

3. **Auth0 CIBA** — `Auth0AsyncAuthzProvider` uses Client-Initiated
   Backchannel Authentication to ask the user out-of-band ("is this agent
   action OK?") via Auth0 Guardian push notifications. Replaces the
   builtin provider when configured.

End state:

- `moa-auth-providers-auth0` (from P1.7) gains three new modules:
  `vault.rs`, `ciba.rs`, plus an extension to the existing user-map for
  per-user linked-connection records.
- `agents` and `agent_templates` tables exist with the full schema; the
  orchestrator exposes `AgentTemplates::{create, list, get, deactivate}`
  and `Agents::{register, list, get, deactivate, grant_can_act_as}`.
- Registering an agent enqueues four outbox tuples in one tx:
  - `agent:<id> tenant tenant:<T>`
  - `agent:<id> operator user:<creator>`
  - `agent_template:<tpl> tenant tenant:<T>` (only on first agent of that
    template; idempotent via outbox)
- `grant_can_act_as(agent_id, user_id)` enqueues `agent:<A> can_act_as
  user:<U>` — the delegation grant that `require_authz_with_delegation`
  enforces.
- `MOA__TOKEN_VAULT__PROVIDER=auth0` and `MOA__ASYNC_AUTHZ__PROVIDER=auth0`
  switch in the Auth0 implementations behind the existing `auth0` feature
  flag.

## Prerequisites

- P1.7 merged. `moa-auth-providers-auth0` exists; `auth0` feature flag is
  the universal gate.
- The reviewer/runner has an Auth0 tenant configured with at least one
  social connection (Google or GitHub) for the Token Vault tests, and
  Auth0 Guardian configured for the CIBA tests.

### 2. `Auth0TokenVaultProvider`

`crates/moa-auth/auth0/src/vault.rs`:

```rust
//! Auth0 Token Vault: retrieves third-party tokens for users.
//!
//! The flow is "token exchange":
//!   1. MOA obtains an M2M access token for its Auth0 Management API role.
//!   2. MOA exchanges the user-context token (or just the user's sub) for
//!      the third-party access token via Auth0's `oauth/token` endpoint
//!      with the urn:auth0:params:oauth:grant-type:token-vault subject.
//!   3. Auth0 returns the third-party token; MOA hands it to the caller.
//!
//! MOA never stores the third-party token. Caching at the call site (the
//! tool that uses the token) is the caller's responsibility, and should
//! use the token's `expires_in` to bound lifetime.

use async_trait::async_trait;
use chrono::{Duration as ChronoDuration, Utc};
use moa_core::traits::{TokenVaultError, TokenVaultProvider, VaultToken};
use secrecy::SecretString;
use serde::Deserialize;
use sqlx::PgPool;
use std::sync::Arc;
use std::time::Duration;
use uuid::Uuid;

pub struct Auth0TokenVaultProvider {
    http: reqwest::Client,
    domain: String,
    client_id: String,
    client_secret: SecretString,
    /// Audience for the Management API; needed for the M2M token used to
    /// look up `sub` -> linked connections.
    management_audience: String,
    pool: Arc<PgPool>,
    /// Cached M2M token; refreshed in-process.
    m2m_token: Arc<tokio::sync::RwLock<Option<(SecretString, chrono::DateTime<Utc>)>>>,
}

impl Auth0TokenVaultProvider {
    pub fn new(
        domain: String,
        client_id: String,
        client_secret: SecretString,
        management_audience: String,
        pool: Arc<PgPool>,
    ) -> Self {
        Self {
            http: reqwest::Client::builder()
                .timeout(Duration::from_secs(10))
                .build().expect("reqwest"),
            domain: domain.trim_end_matches('/').to_string(),
            client_id, client_secret, management_audience, pool,
            m2m_token: Arc::new(tokio::sync::RwLock::new(None)),
        }
    }

    async fn m2m_token(&self) -> Result<SecretString, TokenVaultError> {
        use secrecy::ExposeSecret;
        // Fast path.
        {
            let r = self.m2m_token.read().await;
            if let Some((t, exp)) = &*r {
                if *exp > Utc::now() + ChronoDuration::seconds(60) {
                    return Ok(t.clone());
                }
            }
        }
        // Slow path: fetch a fresh M2M token.
        #[derive(Deserialize)]
        struct M2MResp { access_token: String, expires_in: i64 }
        let resp: M2MResp = self.http
            .post(format!("https://{}/oauth/token", self.domain))
            .json(&serde_json::json!({
                "grant_type": "client_credentials",
                "client_id": self.client_id,
                "client_secret": self.client_secret.expose_secret(),
                "audience": self.management_audience,
            }))
            .send().await
            .map_err(|e| TokenVaultError::Unavailable(format!("m2m: {e}")))?
            .error_for_status()
            .map_err(|e| TokenVaultError::Unavailable(format!("m2m status: {e}")))?
            .json().await
            .map_err(|e| TokenVaultError::Unavailable(format!("m2m parse: {e}")))?;
        let token = SecretString::new(resp.access_token);
        let expires = Utc::now() + ChronoDuration::seconds(resp.expires_in);
        let mut w = self.m2m_token.write().await;
        *w = Some((token.clone(), expires));
        Ok(token)
    }
}

#[async_trait]
impl TokenVaultProvider for Auth0TokenVaultProvider {
    async fn get_token(
        &self,
        user_id: Uuid,
        connection_name: &str,
    ) -> Result<VaultToken, TokenVaultError> {
        // 1. Look up the Auth0 sub for this user_id from auth0_user_map.
        let sub: Option<(String,)> = sqlx::query_as(
            "SELECT sub FROM auth0_user_map WHERE user_id = $1 LIMIT 1"
        )
        .bind(user_id)
        .fetch_optional(&*self.pool).await
        .map_err(|e| TokenVaultError::Internal(format!("db: {e}")))?;
        let sub = sub.ok_or(TokenVaultError::NotLinked)?.0;

        // 2. Confirm this user has linked the named connection.
        let linked: Option<(String,)> = sqlx::query_as(
            "SELECT external_sub FROM linked_connections
             WHERE user_id = $1 AND connection_name = $2"
        )
        .bind(user_id)
        .bind(connection_name)
        .fetch_optional(&*self.pool).await
        .map_err(|e| TokenVaultError::Internal(format!("db: {e}")))?;
        if linked.is_none() {
            return Err(TokenVaultError::NotLinked);
        }

        // 3. Exchange for the third-party token via Auth0's Token Vault.
        use secrecy::ExposeSecret;
        let m2m = self.m2m_token().await?;
        #[derive(Deserialize)]
        struct VaultResp {
            access_token: String,
            expires_in: Option<i64>,
            #[serde(default)] scope: String,
        }
        let resp: VaultResp = self.http
            .post(format!("https://{}/oauth/token", self.domain))
            .bearer_auth(m2m.expose_secret())
            .json(&serde_json::json!({
                "grant_type": "urn:auth0:params:oauth:grant-type:token-vault",
                "subject_token": sub,
                "subject_token_type": "urn:auth0:params:oauth:token-type:auth0-user",
                "connection": connection_name,
            }))
            .send().await
            .map_err(|e| TokenVaultError::Unavailable(format!("exchange: {e}")))?
            .error_for_status()
            .map_err(|e| TokenVaultError::Unavailable(format!("exchange status: {e}")))?
            .json().await
            .map_err(|e| TokenVaultError::Unavailable(format!("exchange parse: {e}")))?;

        let scopes = if resp.scope.is_empty() {
            Vec::new()
        } else {
            resp.scope.split_whitespace().map(String::from).collect()
        };
        let expires_at = resp.expires_in.map(|s| Utc::now() + ChronoDuration::seconds(s));

        Ok(VaultToken {
            access_token: SecretString::new(resp.access_token),
            expires_at,
            scopes,
        })
    }

    async fn list_connections(
        &self,
        user_id: Uuid,
    ) -> Result<Vec<String>, TokenVaultError> {
        let rows: Vec<(String,)> = sqlx::query_as(
            "SELECT connection_name FROM linked_connections WHERE user_id = $1"
        )
        .bind(user_id)
        .fetch_all(&*self.pool).await
        .map_err(|e| TokenVaultError::Internal(format!("db: {e}")))?;
        Ok(rows.into_iter().map(|(c,)| c).collect())
    }

    fn name(&self) -> &'static str { "auth0" }
}
```

### 3. Webhook for linked-connections population

The `linked_connections` table is populated by an Auth0 webhook OR by
periodic polling. The webhook is preferred (push, not pull). Add a route
to `moa-edge`:

`crates/moa-edge/src/routes.rs` — extend the router (gated behind
`#[cfg(feature = "auth0")]`):

```rust
#[cfg(feature = "auth0")]
.route("/v1/webhooks/auth0/connection-linked", post(handle_auth0_connection_webhook))
```

Handler verifies an Auth0 webhook signature (`Auth0-Signature` header
HMAC of the body with a preshared secret from
`MOA__AUTH__AUTH0__WEBHOOK_SECRET`), then inserts into
`linked_connections`. The body format is whatever an Auth0 Action emits;
document the Action's emit shape in the setup doc.

### 4. `Auth0AsyncAuthzProvider` (CIBA)

`crates/moa-auth/auth0/src/ciba.rs`:

```rust
//! Auth0 Client-Initiated Backchannel Authentication.
//!
//! The flow:
//!   1. Handler calls request_approval; we POST to Auth0's
//!      /bc-authorize with the user's `login_hint` (their Auth0 sub).
//!      Auth0 pushes a Guardian notification to the user's phone.
//!   2. We get back an `auth_req_id` (Auth0's handle for the pending
//!      approval). Store it in the ApprovalHandle.provider_specific.
//!   3. A background task polls /oauth/token with the auth_req_id until
//!      pending becomes approved | denied | timeout. On final state, the
//!      task resolves the Restate awakeable.
//!
//! Polling vs streaming: Auth0 CIBA is poll-only. We poll at 2-second
//! intervals up to the configured timeout (default 15 min).

use async_trait::async_trait;
use chrono::{Duration as ChronoDuration, Utc};
use moa_core::traits::{
    ApprovalDecision, ApprovalHandle, ApprovalRequest, AsyncAuthzError, AsyncAuthzProvider,
};
use secrecy::{ExposeSecret, SecretString};
use serde::Deserialize;
use sqlx::PgPool;
use std::sync::Arc;
use std::time::Duration;
use tokio::time::sleep;
use uuid::Uuid;

pub struct Auth0AsyncAuthzProvider {
    http: reqwest::Client,
    domain: String,
    client_id: String,
    client_secret: SecretString,
    pool: Arc<PgPool>,
    /// Same awakeable resolver shape as the builtin reaper uses.
    resolver: Arc<dyn crate::AwakeableResolver>,
}

impl Auth0AsyncAuthzProvider {
    pub fn new(
        domain: String,
        client_id: String,
        client_secret: SecretString,
        pool: Arc<PgPool>,
        resolver: Arc<dyn crate::AwakeableResolver>,
    ) -> Self {
        Self {
            http: reqwest::Client::builder()
                .timeout(Duration::from_secs(30))
                .build().expect("reqwest"),
            domain: domain.trim_end_matches('/').to_string(),
            client_id, client_secret, pool, resolver,
        }
    }
}

#[async_trait]
impl AsyncAuthzProvider for Auth0AsyncAuthzProvider {
    async fn request_approval(
        &self,
        request: ApprovalRequest,
    ) -> Result<ApprovalHandle, AsyncAuthzError> {
        // 1. Look up the Auth0 sub for deciding_user_id.
        let sub_row: Option<(String,)> = sqlx::query_as(
            "SELECT sub FROM auth0_user_map WHERE user_id = $1 LIMIT 1"
        )
        .bind(request.deciding_user_id)
        .fetch_optional(&*self.pool).await
        .map_err(|e| AsyncAuthzError::Internal(format!("db: {e}")))?;
        let sub = sub_row
            .ok_or_else(|| AsyncAuthzError::Internal(
                "user has no auth0 sub; cannot CIBA them".into()
            ))?.0;

        // 2. POST /bc-authorize.
        #[derive(Deserialize)]
        struct BcResp { auth_req_id: String, expires_in: i64, interval: u64 }
        let resp: BcResp = self.http
            .post(format!("https://{}/bc-authorize", self.domain))
            .form(&[
                ("client_id", self.client_id.as_str()),
                ("client_secret", self.client_secret.expose_secret()),
                ("scope", "openid"),
                ("login_hint", &format!("sub={}", sub)),
                ("binding_message", &request.action_summary),
            ])
            .send().await
            .map_err(|e| AsyncAuthzError::Unavailable(format!("ciba: {e}")))?
            .error_for_status()
            .map_err(|e| AsyncAuthzError::Unavailable(format!("ciba status: {e}")))?
            .json().await
            .map_err(|e| AsyncAuthzError::Unavailable(format!("ciba parse: {e}")))?;

        let handle = ApprovalHandle {
            id: Uuid::new_v4(),
            awakeable_id: request.awakeable_id.clone(),
            provider_specific: serde_json::json!({
                "kind": "ciba",
                "auth_req_id": resp.auth_req_id.clone(),
                "interval": resp.interval,
                "expires_in": resp.expires_in,
            }),
        };

        // 3. Spawn the polling task. The task drops itself when the auth
        // request is no longer pending. If MOA crashes, the awakeable
        // times out via Restate's own timeout (request.timeout); on next
        // boot, a reaper sweep (P1.6's pattern) catches orphaned rows.
        let domain = self.domain.clone();
        let client_id = self.client_id.clone();
        let client_secret = self.client_secret.clone();
        let http = self.http.clone();
        let resolver = self.resolver.clone();
        let awakeable_id = request.awakeable_id.clone();
        let auth_req_id = resp.auth_req_id;
        let interval_s = resp.interval.max(2);
        let deadline = Utc::now() + ChronoDuration::seconds(resp.expires_in);

        tokio::spawn(async move {
            loop {
                if Utc::now() >= deadline {
                    let payload = serde_json::json!({ "outcome": "timeout" });
                    let _ = resolver.resolve(&awakeable_id, &payload).await;
                    return;
                }
                sleep(Duration::from_secs(interval_s)).await;

                #[derive(Deserialize)]
                struct PollResp {
                    #[serde(default)] error: Option<String>,
                    #[serde(default)] error_description: Option<String>,
                    #[serde(default)] access_token: Option<String>,
                }
                let r = http
                    .post(format!("https://{}/oauth/token", domain))
                    .form(&[
                        ("grant_type", "urn:openid:params:grant-type:ciba"),
                        ("auth_req_id", auth_req_id.as_str()),
                        ("client_id", client_id.as_str()),
                        ("client_secret", client_secret.expose_secret()),
                    ])
                    .send().await;
                let Ok(resp) = r else { continue };
                let body: PollResp = match resp.json().await {
                    Ok(b) => b,
                    Err(_) => continue,
                };

                match (body.error.as_deref(), body.access_token.as_deref()) {
                    (None, Some(_)) => {
                        let payload = serde_json::json!({ "outcome": "approved" });
                        let _ = resolver.resolve(&awakeable_id, &payload).await;
                        return;
                    }
                    (Some("authorization_pending"), _) => continue,
                    (Some("slow_down"), _) => {
                        sleep(Duration::from_secs(interval_s)).await;
                        continue;
                    }
                    (Some("expired_token"), _) => {
                        let payload = serde_json::json!({ "outcome": "timeout" });
                        let _ = resolver.resolve(&awakeable_id, &payload).await;
                        return;
                    }
                    (Some("access_denied"), _) => {
                        let payload = serde_json::json!({
                            "outcome": "denied",
                            "reason": body.error_description,
                        });
                        let _ = resolver.resolve(&awakeable_id, &payload).await;
                        return;
                    }
                    (Some(other), _) => {
                        tracing::error!(error = %other, "ciba poll error");
                        let payload = serde_json::json!({
                            "outcome": "denied",
                            "reason": format!("ciba error: {other}"),
                        });
                        let _ = resolver.resolve(&awakeable_id, &payload).await;
                        return;
                    }
                    (None, None) => continue,
                }
            }
        });

        Ok(handle)
    }

    fn name(&self) -> &'static str { "auth0_ciba" }
}
```

The `AwakeableResolver` trait from P1.6 is shared between the builtin
reaper and the CIBA poller. Move its definition from
`crates/moa-orchestrator/src/services/approvals_reaper.rs` to a shared
location — either `moa-core::traits` (preferred) or a new
`moa-authz::resolver` module. The Auth0 crate consumes the trait.

`resolver_from_runtime()` is a helper that the orchestrator's `main.rs`
provides (it has access to the Restate context). For now, the bundle's
build function takes an optional `Arc<dyn AwakeableResolver>` parameter
that the orchestrator passes through; the edge passes `None` and the
match arm errors loudly if the edge tries to build Auth0 async authz
(the edge should not — async authz is an orchestrator concern).

### 6. Agent template service

`crates/moa-orchestrator/src/services/agent_templates.rs`:

Restate service with handlers:

- `AgentTemplates::create(name, description, instructions, allowed_tools)`
  → requires `tenant.admin`. Writes the row + enqueues
  `agent_template:<id> tenant tenant:<T>` via outbox.
- `AgentTemplates::list()` → requires `tenant.member`. Returns templates
  this caller can see (FGA ListObjects with `member` relation, or simple
  per-tenant filter for v1).
- `AgentTemplates::get(id)` → requires `agent_template.creator` OR
  `tenant.admin`.
- `AgentTemplates::deactivate(id)` → requires `agent_template.creator`.
  Sets `deactivated_at`; new agent instantiation is rejected. Existing
  agent instances are not auto-deactivated.

### 7. Agent service

`crates/moa-orchestrator/src/services/agents.rs`:

- `Agents::register(template_id, display_name)` → requires
  `agent_template.creator` (or `tenant.admin`). Writes the agents row;
  enqueues:
  - `agent:<new> tenant tenant:<T>`
  - `agent:<new> operator user:<creator>`
- `Agents::list()` → returns agents the caller operates.
- `Agents::get(id)` → requires `agent.operator` or `tenant.admin`.
- `Agents::deactivate(id)` → requires `agent.operator`. Sets `status =
  'deactivated'` + `deactivated_at`. Enqueues `delete` outbox tuples for
  ALL of this agent's grants:
  - All `agent:<id> can_act_as user:<*>` tuples (discoverable via FGA's
    `Read` API for `agent:<id> can_act_as`).
  - The `operator` tuple.
  - The `tenant` tuple.
  Also: revoke any API keys whose `owner_agent_id = <id>`. Hooks into the
  api_keys revocation code path from P1.5 (reason: "agent_deactivation_cascade").
- `Agents::grant_can_act_as(agent_id, user_id)` → requires `agent.operator`
  AND `user_id == operator OR operator has admin on user's tenant`.
  Caller cannot grant agent the right to act as a user they don't have
  authority over. Enqueues `agent:<A> can_act_as user:<U>`.
- `Agents::revoke_can_act_as(agent_id, user_id)` → enqueues delete tuple.

Handler implementations follow the same shape as `services/api_keys.rs`
(P1.5): require_authz, transaction, outbox enqueues, commit.

### 10. Docs

Add `docs/operations/agent-lifecycle.md`:

```markdown
# Agent lifecycle

Agents are first-class principals in MOA — they have FGA subject identity
(`agent:<uuid>`) and can be granted permissions directly. This document
walks through the lifecycle from template creation through deactivation.

## Templates vs instances

An **agent template** is a class definition: a name, description, system
prompt (instructions), and an allowlist of tool names. Templates are
created by tenant admins.

An **agent** is an instance: a specific deployment with its own UUID, its
own can_act_as grants, and its own audit trail. Multiple agents can share
a template.

## Permissions model

- An agent has tuples placed by `Agents::register`:
  - `agent:<id> tenant tenant:<T>`
  - `agent:<id> operator user:<creator>`
- An agent inherits NONE of its operator's permissions automatically.
  Specifically, an operator's workspace membership does NOT propagate to
  the agent.
- To let an agent do work, an operator must either:
  1. Grant the agent the resource permission directly (e.g.,
     `agent:<id> editor workspace:<W>`). The agent acts as itself.
  2. Grant the agent `can_act_as` for the operator (or another user),
     and have the agent set `Acting-On-Behalf-Of: <user>` on requests.
     The agent still must have the resource permission separately;
     `can_act_as` only gates whether the delegation is permitted.

## Deactivation

`Agents::deactivate` is a tear-down operation:

1. Marks the row `status='deactivated'`.
2. Enqueues outbox `delete` for every `can_act_as` tuple this agent holds.
3. Enqueues outbox `delete` for `operator` and `tenant` tuples.
4. Revokes every API key whose `owner_agent_id = <agent_id>` with reason
   `agent_deactivation_cascade`.
5. Existing sessions owned by the agent are NOT auto-cancelled in P1.8.
   Operators must cancel them separately (or wait for P1.9's full
   deactivation cascade, which can be triggered manually by deleting
   the operator user).

Deactivation is reversible only via undo migration; there is no
`reactivate` handler.
```

## Notes

- **The Token Vault never stores tokens in MOA**: this is the design's
  privacy and security center of gravity. The exchange endpoint returns
  tokens just-in-time; callers cache by-call but never persist. Auth0
  rotates tokens server-side; we benefit from the rotation for free.
- **`urn:auth0:params:oauth:grant-type:token-vault` is Auth0-specific**:
  generic OIDC token exchange (RFC 8693) does not have an out-of-the-box
  equivalent. If a customer asks for self-hosted IdP token vault, they
  will need to run a custom token exchange service; we cannot provide
  a portable `TokenVaultProvider` impl beyond Auth0 without that.
- **CIBA requires Auth0 Guardian** (or a similar OOB authenticator). The
  user's Auth0 account must have a Guardian enrollment; without it
  `/bc-authorize` returns an error and request_approval fails. Document
  this prominently; the failure mode is the #1 user-confusion path.
- **CIBA poll task lifecycle**: the poll task is fire-and-forget. If MOA
  crashes mid-poll, the awakeable times out via Restate's own timer
  (the `timeout` field on ApprovalRequest). On restart, a reaper sweep
  catches orphans. Do NOT try to checkpoint the auth_req_id in Postgres
  for resumption — Auth0 documents that auth_req_ids are short-lived
  (typically 10 minutes), so checkpoint resumption rarely helps.
- **`agent_template` deactivation does not auto-deactivate instances**:
  this is deliberate. A template change must not silently break running
  agents. Operators deactivate templates AND deactivate each instance
  separately. P1.10 may add a cascade option behind a `--force` flag.
- **`Agents::deactivate` cascade is bounded**: it tears down operator,
  tenant, and can_act_as tuples plus api_keys. It does NOT remove
  resource-permission tuples (e.g., `agent:<id> editor workspace:<W>`)
  because we cannot list them without a `Read` over all FGA tuples
  (expensive). In practice, agents almost never have direct resource
  tuples — operators grant via can_act_as. A future prompt may add an
  `--also-resource-tuples` flag that does the expensive Read+delete.
- **Linked-connection webhook signature**: Auth0 signs webhook payloads
  with HMAC-SHA256 using a tenant-configured secret. Verify in
  constant time (`constant_time::verify` from `subtle` crate). Failing
  to verify in constant time leaks the secret over time via timing.
- **Why webhook over polling**: polling the Management API for every
  user's connections every minute is expensive and slow. The webhook
  is push-driven and lands within seconds of link completion. Polling
  remains as a fallback only — implement webhook; defer polling.
- **`grant_can_act_as` authorization check**: the prompt's pseudocode
  shows the agent's operator can grant. A stricter policy would require
  the user being delegated to (the `user` param) to also consent. P1.8
  does not require user consent; this is a knob for P3 if needed.

## What P1.9 expects

- `users` table exists with `source` and `deactivated_at` columns.
- `agents`, `agent_templates`, `api_keys`, `linked_connections` tables
  exist with consistent FK shape — P1.9's deactivation cascade walks
  these.
- All agent lifecycle handlers enforce `require_authz_with_delegation`
  and enqueue/dequeue outbox tuples — patterns P1.9 mirrors for SCIM
  user-deactivation.
- `Auth0TokenVaultProvider` and `Auth0AsyncAuthzProvider` are usable;
  P1.9 does not extend them but does emit OCSF events (P1.10 territory)
  for token retrievals and approval decisions.
