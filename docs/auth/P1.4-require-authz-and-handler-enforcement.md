# P1.4 — `require_authz()` Helpers and First Handler Enforcement

## Purpose

Make the orchestrator's high-value handlers refuse unauthorized requests
and emit outbox-backed FGA tuples for the resources they create. This
prompt is where authorization stops being plumbing and starts shaping
runtime behavior.

End state:

- `moa-authz::require::{require_authz, require_authz_with_delegation}` are
  the canonical entry points; every handler authz check goes through them.
- The orchestrator's three highest-value handlers — session create, turn
  dispatch, agent register — are wired up:
  - Session create: caller must be `workspace.member`; side-effect outbox
    tuple `<subject> owner session:<id>` written in the same Postgres
    transaction.
  - Turn dispatch: caller must be `session.participant`.
  - Agent register: caller must be `tenant.admin`; side-effects write
    `agent:<id> tenant tenant:<T>` and `agent:<id> operator user:<creator>`.
- A subject-derivation helper centralizes the FGA subject-string convention
  (api_key prefix wins; otherwise identity_type + id).
- Delegation: if `identity.acting_on_behalf_of` is set, `require_authz_with_delegation`
  *also* verifies the agent has `can_act_as` for the named user.
- Deny-by-default review rule lands in `AGENTS.md`: every new handler must
  either call `require_authz`/`require_authz_with_delegation` or carry a
  one-line `// SAFETY: ...` justification explaining why no check is
  needed. PR reviewers fail PRs that violate this.

This prompt does not yet refactor the second-tier handlers (search,
checkpoint, etc.) — those land incrementally in their own future prompts.
It does not introduce procedural macros; explicit calls only.

## Prerequisites

- P1.3 merged. `moa-edge` injects headers; orchestrator extracts them.
- `MOA__AUTH__HEADER_TRUST` defaults to `Lenient` for dev convenience; this
  prompt does NOT switch it to `Strict` (production deployments do).

### 1. Add `moa-authz::require` module

`crates/moa-auth/authz/src/require.rs`:

```rust
//! `require_authz` and `require_authz_with_delegation` are the canonical
//! entry points for handler authorization checks. Every handler that
//! enforces authz calls one of these; no handler should call
//! `FgaClient::check` directly.
//!
//! The deny path is explicit: callers receive a structured error and are
//! expected to translate to the wire-level forbidden response in their
//! handler shim. We do not panic, do not log-and-allow, do not "fail
//! open" under any circumstance.

use crate::client::FgaClient;
use crate::error::AuthzError;
use moa_authz_schema::{ObjectType, Relation};
use moa_core::traits::{Identity, IdentityType};
use thiserror::Error;
use uuid::Uuid;

#[derive(Debug, Error)]
pub enum AuthzCheckError {
    #[error("forbidden: identity {subject} not {relation} on {object_type}:{object_id}")]
    Forbidden {
        subject: String,
        object_type: ObjectType,
        object_id: Uuid,
        relation: Relation,
    },
    #[error("authz engine error: {0}")]
    Engine(#[from] AuthzError),
}

/// Verify that `identity` has `relation` on `(object_type, object_id)`.
///
/// On `Ok(())`: the relation holds in OpenFGA at the time of the call.
/// On `Err(Forbidden)`: the relation does not hold; caller must deny.
/// On `Err(Engine)`: the authz engine itself failed. Treat as a deny at
/// the handler layer (5xx not 403) — never fail open.
pub async fn require_authz(
    fga: &FgaClient,
    identity: &Identity,
    object_type: ObjectType,
    object_id: Uuid,
    relation: Relation,
) -> Result<(), AuthzCheckError> {
    let subject = fga_subject(identity);
    let object = format!("{}:{}", object_type, object_id);
    let allowed = fga.check(&subject, &relation.to_string(), &object).await?;
    if !allowed {
        return Err(AuthzCheckError::Forbidden {
            subject, object_type, object_id, relation,
        });
    }
    Ok(())
}

/// Like `require_authz`, but if the identity is an agent acting on behalf
/// of a user, also verifies that the agent has `can_act_as` for that user.
///
/// The agent's *own* tuples are still what's checked for the resource
/// permission. Delegation does not silently borrow the underlying user's
/// permissions — the agent must have been granted them directly (typically
/// at agent template instantiation time).
pub async fn require_authz_with_delegation(
    fga: &FgaClient,
    identity: &Identity,
    object_type: ObjectType,
    object_id: Uuid,
    relation: Relation,
) -> Result<(), AuthzCheckError> {
    if let Some(user_id) = identity.acting_on_behalf_of {
        // The agent must be authorized to act for this user.
        if identity.identity_type != IdentityType::Agent {
            return Err(AuthzCheckError::Forbidden {
                subject: fga_subject(identity),
                object_type: ObjectType::Agent,    // placeholder for error shape
                object_id: identity.id,
                relation: Relation::CanActAs,
            });
        }
        let agent_subj = format!("agent:{}", identity.id);
        let user_obj = format!("user:{}", user_id);
        let allowed = fga.check(&agent_subj, "can_act_as", &user_obj).await?;
        if !allowed {
            return Err(AuthzCheckError::Forbidden {
                subject: agent_subj,
                object_type: ObjectType::Tenant,    // shape doesn't have a User variant
                object_id: user_id,
                relation: Relation::CanActAs,
            });
        }
    }
    require_authz(fga, identity, object_type, object_id, relation).await
}

/// Canonical FGA subject derivation. API key takes precedence — when a
/// request is authenticated via an API key, the FGA subject is
/// `api_key:<id>`, not the owner. Scopes are tuples on the api_key subject;
/// using the api_key subject is how scoped keys actually narrow access.
pub fn fga_subject(identity: &Identity) -> String {
    if let Some(key_id) = identity.api_key_id {
        return format!("api_key:{}", key_id);
    }
    match identity.identity_type {
        IdentityType::User => format!("user:{}", identity.id),
        IdentityType::Agent => format!("agent:{}", identity.id),
        IdentityType::Service => format!("service:{}", identity.id),
    }
}
```

Re-export at `crates/moa-auth/authz/src/lib.rs`:

```rust
pub mod require;
pub use require::{require_authz, require_authz_with_delegation, fga_subject, AuthzCheckError};
```

```rust
// crates/moa-orchestrator/src/handlers/authz_shim.rs
use moa_authz::AuthzCheckError;
use restate_sdk::prelude::HandlerError;

pub fn translate_authz_error(e: AuthzCheckError) -> HandlerError {
    match e {
        AuthzCheckError::Forbidden { subject, object_type, object_id, relation } => {
            tracing::info!(
                deny.subject = %subject,
                deny.object = format!("{}:{}", object_type, object_id),
                deny.relation = %relation,
                "authz denied"
            );
            HandlerError::with_status(403, format!("forbidden: {} not {} on {}:{}", subject, relation, object_type, object_id))
        }
        AuthzCheckError::Engine(e) => {
            tracing::error!(error = %e, "authz engine error; failing closed");
            HandlerError::with_status(503, "authorization engine unavailable")
        }
    }
}
```

(The exact `HandlerError` API depends on the Restate SDK version — adapt the
constructor as needed. The principle is: 403 for Forbidden, 5xx for Engine.)

### 4. Session create — `require_authz` + outbox

Find the session-create handler (likely `session_store::SessionStore::create_session`
or `session::Session::post_message` first-call path; pick the one that actually
allocates the session_id). The new flow inside the handler:

```rust
// Pseudocode; adapt to actual handler shape.
async fn create_session(ctx: Context<'_>, req: CreateSessionRequest) -> Result<SessionMeta, HandlerError> {
    let identity = ctx::current_identity(ctx)
        .map_err(|e| HandlerError::with_status(400, format!("bad identity: {e}")))?
        .ok_or_else(|| HandlerError::with_status(401, "identity required"))?;

    let fga = fga_client(); // however the orchestrator exposes it
    let pool = pg_pool();

    // ---- authz check: caller must be workspace.member ----
    moa_authz::require_authz_with_delegation(
        fga,
        &identity,
        moa_authz_schema::ObjectType::Workspace,
        req.workspace_id,
        moa_authz_schema::Relation::Member,
    )
    .await
    .map_err(handlers::authz_shim::translate_authz_error)?;

    // ---- create session + enqueue outbox tuple in one tx ----
    let session_id = uuid::Uuid::new_v4();
    let mut tx = pool.begin().await
        .map_err(|e| HandlerError::with_status(500, format!("db: {e}")))?;

    sqlx::query(
        "INSERT INTO sessions (id, tenant_id, workspace_id, user_id, ...) VALUES ($1, $2, $3, $4, ...)"
    )
    .bind(session_id)
    .bind(identity.tenant_id)
    .bind(req.workspace_id)
    // ... other columns
    .execute(&mut *tx)
    .await
    .map_err(|e| HandlerError::with_status(500, format!("db: {e}")))?;

    // Owner tuple: who created the session owns it.
    let owner_subject = subject_uuid(&identity);
    let owner_user_type = subject_user_type(&identity);
    let owner_tuple = moa_authz_schema::TupleKey::new(
        owner_user_type,
        owner_subject,
        moa_authz_schema::Relation::Owner,
        moa_authz_schema::ObjectType::Session,
        session_id,
    );
    moa_authz::outbox::enqueue(&mut *tx, moa_authz_schema::TupleOp::Write, &owner_tuple, Some(identity.tenant_id))
        .await
        .map_err(|e| HandlerError::with_status(500, format!("outbox: {e}")))?;

    // Workspace-parent tuple: lets workspace-level perms cascade to the session.
    let parent_tuple = moa_authz_schema::TupleKey::new(
        moa_authz_schema::UserType::User,  // unused for `workspace -> session` edge; see note below
        req.workspace_id,
        moa_authz_schema::Relation::Workspace,
        moa_authz_schema::ObjectType::Session,
        session_id,
    );
    // The outbox stores wire format directly, so the user-type field for the
    // parent tuple is fine: enqueue serializes via `user_wire()` which prints
    // "workspace:<uuid>" only if user_type is one of our subject types.
    // We bypass that by overriding via a raw helper. Add `enqueue_raw` to
    // `moa-authz::outbox` for this case (parent edges with non-user subjects).

    moa_authz::outbox::enqueue_raw(
        &mut *tx,
        moa_authz_schema::TupleOp::Write,
        &format!("workspace:{}", req.workspace_id),
        "workspace",
        &format!("session:{}", session_id),
        Some(identity.tenant_id),
    )
    .await
    .map_err(|e| HandlerError::with_status(500, format!("outbox: {e}")))?;

    tx.commit().await.map_err(|e| HandlerError::with_status(500, format!("db commit: {e}")))?;

    Ok(SessionMeta { id: session_id, /* ... */ })
}

fn subject_uuid(id: &moa_core::traits::Identity) -> uuid::Uuid {
    if let Some(k) = id.api_key_id { return k; }
    id.id
}
fn subject_user_type(id: &moa_core::traits::Identity) -> moa_authz_schema::UserType {
    if id.api_key_id.is_some() { return moa_authz_schema::UserType::ApiKey; }
    match id.identity_type {
        moa_core::traits::IdentityType::User => moa_authz_schema::UserType::User,
        moa_core::traits::IdentityType::Agent => moa_authz_schema::UserType::Agent,
        moa_core::traits::IdentityType::Service => moa_authz_schema::UserType::User, // services treated as users in v1
    }
}
```

### 4a. Add `outbox::enqueue_raw`

Parent edges like `workspace -> session` have a non-user subject
(`workspace:<id>`), so the typed `TupleKey` API doesn't fit cleanly. Add a
raw helper to `moa-authz::outbox`:

```rust
pub async fn enqueue_raw<'e, E: sqlx::PgExecutor<'e>>(
    exec: E,
    op: moa_authz_schema::TupleOp,
    user_wire: &str,
    relation: &str,
    object_wire: &str,
    tenant_id: Option<Uuid>,
) -> Result<(), AuthzError> {
    let idem = format!(
        "{}-{}-{}-{}-v{}",
        op, object_wire, relation, user_wire,
        moa_authz_schema::MODEL_VERSION,
    );
    sqlx::query(
        r#"
        INSERT INTO authz_outbox
            (idempotency_key, op, tuple_user, tuple_relation, tuple_object, model_version, tenant_id)
        VALUES ($1, $2, $3, $4, $5, $6, $7)
        ON CONFLICT (idempotency_key) DO NOTHING
        "#,
    )
    .bind(&idem)
    .bind(op.to_string())
    .bind(user_wire)
    .bind(relation)
    .bind(object_wire)
    .bind(moa_authz_schema::MODEL_VERSION as i32)
    .bind(tenant_id)
    .execute(exec)
    .await?;
    Ok(())
}
```

### 7. Deny-by-default review rule

Add a section to `AGENTS.md` titled "Authorization review rule":

```markdown
## Authorization review rule

Every handler that touches data on behalf of a caller MUST either:

1. Call `moa_authz::require_authz` or `require_authz_with_delegation` with
   the appropriate `(ObjectType, object_id, Relation)`. The check happens
   before any reads of the protected resource. OR
2. Carry a one-line `// SAFETY: ...` justification immediately above the
   handler signature explaining why no check is needed. Acceptable
   justifications: "purely informational; no resource-specific data",
   "health/observability endpoint", "called only from another handler that
   has already checked".

PRs that violate this rule are returned for revision. The reviewer is
explicitly responsible for verifying the justification is correct; this is
not a CI-enforceable rule because it depends on judgment about the data
the handler returns.

Common mistakes:

- Reading the resource first to determine the workspace_id, then checking
  authz. Wrong order: an unauthorized caller has already exfiltrated the
  resource's existence and any read-able fields. Always check first.
- Using `require_authz` for a write that should use
  `require_authz_with_delegation`. If the handler accepts requests from
  agents, use the delegation variant.
- Forgetting to enqueue the inverse outbox tuple on resource deletion. If
  create-handlers enqueue write tuples, delete-handlers must enqueue
  delete tuples in the same transaction. Stale tuples in OpenFGA grant
  phantom access after a resource is deleted.
```

## Notes

- **Why "fail closed" on engine error, with 503 not 403**: a 403 communicates
  "you are not authorized." A 503 communicates "we couldn't determine
  authorization right now." The distinction matters for client retry
  behavior and for incident triage — operational outages should not look
  like permission denials.
- **Why API key is preferred over the underlying user/agent for the FGA
  subject**: scoped API keys narrow access. If we resolved the api_key
  to its owner and used the owner's tuples, the api_key scope would be
  silently ignored. By using `api_key:<id>` as the subject, the api_key's
  tuples (set in P1.5) define exactly what it can do.
- **Delegation does NOT silently borrow user permissions**: the agent must
  have been granted the resource permission directly. This is a deliberate
  design choice from the handoff §4.2. If you want an agent to act with a
  user's full powers, write the tuples explicitly at agent provisioning
  time. The `can_act_as` relation is a gate on whether the agent can act
  on the user's behalf at all; it is not a "borrow all permissions" grant.
- **`require_authz_with_delegation` rejects non-agent identities that have
  `acting_on_behalf_of` set** rather than silently ignoring the field. A
  user identity with `acting_on_behalf_of` is malformed (came from a
  buggy edge or a forged header); refusing is the safest signal.
- **Why outbox writes go in the same Postgres transaction as the resource
  write**: this is the entire point of the transactional outbox. If the
  resource INSERT commits but the tuple INSERT rolls back, FGA permanently
  disagrees with Postgres. If they're in one tx, either both commit or
  both don't; the poller is the only point where eventual consistency is
  visible, and the poller is idempotent.
- **The session creation enqueues two tuples**: the owner tuple is the
  direct grant; the parent (`workspace -> session`) edge lets workspace
  membership cascade. Without the parent edge, workspace members who
  didn't create the session wouldn't be participants — a regression vs.
  pre-auth behavior. Same pattern applies to documents (knowledge_base
  parent), agent_templates (tenant parent), etc.
- **Parent-edge tuples are conceptually system-owned, not user-owned**.
  In production you may want a separate writer (a periodic reconciliation
  job) ensure these edges are correct. P1.4 writes them inline because
  they're cheap and the outbox handles failure.
- **`HandlerError::with_status` is a Restate-SDK 0.8 method**; older
  versions name it differently. Adapt the shim's error translation to
  whatever the SDK actually exposes.
- **The deny-by-default rule is human-enforced**, not CI-enforced.
  Tooling can flag handlers that don't reference `require_authz`, but
  cannot judge whether the SAFETY comment is correct. PR reviewers carry
  the responsibility. P1.10 may add a metric on handler-level authz
  coverage as a forcing function.

## What P1.5 expects

- `require_authz` / `require_authz_with_delegation` are available and
  battle-tested by integration tests.
- The session-create handler enqueues the owner tuple correctly; P1.5's
  API-key-create flow will mirror this pattern (write the api_key row +
  enqueue `api_key:<new> owner <user>:<owner_user_id>` in one tx).
- `fga_subject(identity)` is the canonical subject derivation; P1.5's
  api-key validator can produce an Identity with `api_key_id` set and
  trust that downstream handlers will use the correct FGA subject.
- The deny-by-default rule is in `AGENTS.md` so P1.5's new endpoints will
  comply by default.
